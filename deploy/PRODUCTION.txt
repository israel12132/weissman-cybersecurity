Weissman — production deployment
================================

Recommended path: Docker Compose (full stack)
---------------------------------------------
From repository root:

  cp PRODUCTION.env.template .env
  # Edit .env: POSTGRES_*, DB_APP_*, DB_AUTH_*, WEISSMAN_JWT_SECRET,
  # WEISSMAN_DESTRUCTIVE_CONFIRM_SECRET (required for destructive actions in prod)

  docker compose up -d --build

Services: postgres (pgvector), redis, backend (weissman-server), worker (weissman-worker), gateway (nginx SPA).

- Migrations run once at backend boot when WEISSMAN_MIGRATE_URL is set.
- REDIS_URL is set automatically in compose for distributed rate limits.
- Worker polls weissman_async_jobs — required for scans and async engines.

Verify: curl -sf http://localhost/api/health

Continuity page (automatic, nothing to switch on): while the backend restarts, migrates or is
rebuilt, the gateway serves the branded Weissman page as HTTP 503 + Retry-After and drops it
on the first 200 from /api/health. Roll out new code with deploy/rebuild.sh (build → recreate
backend/worker with --no-deps → wait for 200 → how long the origin was unreachable).
Runbook: docs/operations/MAINTENANCE-PAGE-AND-ZERO-DOWNTIME-REBUILD.md

Sync migrations locally before deploy:

  bash scripts/check-migration-sync.sh

systemd / VPS (bare metal)
--------------------------
1. Build frontend: ./deploy/build-frontend.sh  (or cd frontend && npm ci && npm run build)
2. Build Rust: cargo build --release -p weissman-server
3. Install units: sudo bash deploy/systemd/install-weissman-systemd.sh
4. Configure /etc/weissman/weissman.env (see deploy/systemd/weissman.env.example):
   - DATABASE_URL, WEISSMAN_JWT_SECRET, WEISSMAN_COOKIE_SECURE=1
   - WEISSMAN_MIGRATE_URL (superuser, for boot migrations)
   - REDIS_URL=redis://127.0.0.1:6379/0 (deploy Redis separately)
   - WEISSMAN_DESTRUCTIVE_CONFIRM_SECRET
5. Enable: sudo systemctl enable --now weissman-server weissman-worker weissman.target
6. Reverse proxy: deploy/Caddyfile or deploy/nginx-weissman.conf
7. Continuity page for the proxy (automatic once installed): sudo bash deploy/maintenance/install.sh
   → /opt/weissman/maintenance (install-weissman-systemd.sh does this too). nginx/Caddy then serve
   the branded 503 page whenever the units cannot answer. Later rollouts: deploy/rebuild.sh.
   Runbook: docs/operations/MAINTENANCE-PAGE-AND-ZERO-DOWNTIME-REBUILD.md

Kubernetes
----------
Manifests in deploy/k8s/:
- backend-deployment.yaml — weissman-server (set WEISSMAN_MIGRATE_URL on one replica or use a Job)
- worker-deployment.yaml — weissman-worker (same image, no migrations)
- redis-deployment.yaml — Redis for rate limits
- gateway-deployment.yaml, ingress.yaml
- maintenance-page-configmap.yaml (generated), maintenance-deployment.yaml — ingress-nginx default
  backend that serves the branded 503 page whenever the gateway has no ready endpoints or answers
  502/503/504 (apply ConfigMap → Deployment → wait for rollout → ingress.yaml).
  Runbook §5: docs/operations/MAINTENANCE-PAGE-AND-ZERO-DOWNTIME-REBUILD.md

Secrets (weissman-secrets): database_url, auth_database_url, migrate_url, jwt_secret,
redis_url, destructive_confirm_secret.

Cloudflare in front (any topology): deploy/cloudflare/maintenance-worker/ serves the same page
from the edge when the whole machine is off (DNS proxied, `npx wrangler deploy`; see its README).

Manual migration (optional)
---------------------------
  export WEISSMAN_MIGRATE_URL=postgres://postgres:PASSWORD@host:5432/weissman
  cargo run --example run_migrate -p weissman-db
